# Protocol v1 compatibility

Protocol versioning is independent from Rust, npm, and Python package versions. A peer accepts an envelope when the protocol major version is `1`; it accepts any v1 minor version when the message type is known and required fields are valid. Unknown optional object fields are ignored.

The `client_hello` envelope offers the client's highest v1 minor. The runtime selects the lower of that offer and its current minor (`1.1`) and returns that selection in the `runtime_hello` envelope. Every later frame in either direction is pinned to the selected envelope version; a same-major version change after the handshake is an `incompatible_version` error. A future v1 offer therefore safely selects `1.1`, while a `1.0` offer retains the exact legacy event and conservative metadata projection.

Protocol 1.1 adds the optional `start_run.payload.request.strategy` field (`adaptive`, `direct`, `declarative_plan`, or `programmatic`), complete public tool safety metadata, provider capability limits, and metadata-only adaptive execution events. When 1.0 is selected, the strategy field must be omitted; every explicit strategy value is rejected before the run starts or any tool effect occurs, while omission retains legacy behavior. Programmatic execution is additionally unavailable unless the sidecar is configured with its sandbox; providers must not advertise it otherwise. Raw provider deltas, speculative results, and private speculation metrics are never protocol fields.

An unknown message type is a structured `unknown_message_type` error, not an ignored command. A different major version is a structured `incompatible_version` error. The runtime never treats a malformed line, stderr output, or an arbitrary process log as protocol traffic.

`get_provider_health` and `get_model_inventory` are typed client commands whose
`provider_health` and `model_inventory` responses are not scoped to a run. They
must not allocate an agent run, access a host tool, or reuse a run callback ID.

Every newline-delimited JSON frame is limited to 256 KiB and depth 64. Request, run, and callback identifiers are non-empty and limited to 256 bytes. Runtime implementations must cap concurrent runs at 16, pending callbacks at 128, and internal event queues at 256 unless future compatible capabilities advertise stricter limits.
